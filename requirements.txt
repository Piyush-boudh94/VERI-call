# Runtime + evaluation dependencies.
#
# torch/torchaudio are pinned to the versions every checkpoint in this repo was
# ACTUALLY trained and calibrated against, measured from the environment that
# produced them rather than assumed:
#
#     python 3.12.12   torch 2.13.0+cu130   torchaudio 2.11.0+cu130
#
# This file previously pinned torch==2.4.0 with a comment claiming that was the
# version the checkpoints were calibrated against. It was not, and nothing ever
# checked: the pin and the environment had drifted apart, so `pip install -r
# requirements.txt` on a fresh machine would have installed a torch nine
# releases away from the one every number in docs/RESULTS.md was measured on.
# run_local.py now compares the running torch against this pin and warns, so
# the two cannot drift silently again.
#
# The +cu130 local version is deliberately NOT pinned here, because the right
# CUDA build depends on the target machine's driver. On Linux the default PyPI
# wheel bundles CUDA and works; on Windows the default wheel is CPU-ONLY and
# the demo will not keep up with real-time audio. See docs/LOCAL_DEPLOYMENT.md
# for the per-platform install line.
# 2.4.0 is what PRODUCED the weights: every checkpoint in checkpoints/ was
# trained in the GPU pod (deploy/gpu-pod.yaml, image
# pytorch/pytorch:2.4.0-cuda12.4-cudnn9-runtime). An earlier edit repinned this
# to 2.13.0 after measuring the HEAD NODE -- which is only where serving and
# offline evaluation run, so it recorded the consumer and not the producer.
#
# Both are validated, on different halves of the project:
#   torch 2.4.0  + torchaudio 2.4.0   training, in the pod, on the MIG slice
#   torch 2.13.0 + torchaudio 2.11.0  serving and eval, on bmu-headnode, CPU
#
# The checkpoints are state_dicts of tensors and load under either, which is
# why the mismatch went unnoticed. run_local.py accepts either and warns on
# anything else.
torch==2.4.0
torchaudio==2.4.0
